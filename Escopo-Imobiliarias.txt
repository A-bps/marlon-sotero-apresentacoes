DOCUMENTO DE ESCOPO E PLANEJAMENTO DA PRIMEIRA VERSÃO
PLATAFORMA DE APRESENTAÇÃO IMOBILIÁRIA PARA CORRETORES
====================================================================

Versão: 1.0
Escopo: somente a primeira versão do produto
Base: escopo funcional revisado

Este documento organiza a primeira versão em seis modelos de trabalho:

1. PRD — Product Requirements Document
2. TRD — Technical Requirements Document
3. Fluxo completo do aplicativo
4. Briefing de design e interface
5. Esquema de back-end e banco de dados
6. Plano de implementação e testes

Não fazem parte deste documento: módulos de vendas, fluxo financeiro, espelho de vendas, CRM, ERP, login do corretor ou cadastro autônomo de novos empreendimentos.


====================================================================
1. PRD — PRODUCT REQUIREMENTS DOCUMENT
====================================================================

1.1 Nome de trabalho

Plataforma de Apresentação Imobiliária para Corretores.

Nome comercial definitivo: será definido posteriormente.


1.2 O que é o produto

É uma aplicação web que permite ao corretor acessar uma página inicial com os empreendimentos contratados e abrir uma experiência interativa específica para cada projeto.

A experiência poderá conter modelo 3D, localização, galeria, plantas, amenities, tour e demais materiais fornecidos para aquele empreendimento.

O corretor poderá copiar um link público do empreendimento e enviá-lo ao cliente. O cliente abrirá esse link diretamente no navegador, sem instalar aplicativo e sem visualizar a tela inicial com os outros empreendimentos do corretor.

O produto será uma única aplicação hospedada em um único domínio. Cada empreendimento será uma configuração e uma página dentro dessa aplicação.


1.3 Problema que o produto resolve

O corretor normalmente envia PDF, imagens, vídeos separados ou links diferentes para apresentar um empreendimento. Esse processo pode ser fragmentado, pouco visual e menos memorável.

A aplicação centraliza a apresentação em uma experiência navegável, permitindo que o corretor envie um único link para o cliente explorar o projeto.

Problemas específicos:

- Excesso de arquivos enviados separadamente.
- Dificuldade de apresentar um empreendimento antes de uma reunião.
- Baixa diferenciação entre corretores.
- Cliente sem uma visão integrada do projeto.
- Falta de uma página personalizada para cada empreendimento.
- Dificuldade de associar o contato do cliente ao corretor que enviou a apresentação.


1.4 Público-alvo principal

Corretor de imóveis que:

- Trabalha com lançamentos ou empreendimentos diferenciados.
- Precisa enviar apresentações aos clientes.
- Quer se diferenciar de outros corretores.
- Atua com um ou mais empreendimentos contratados.
- Não quer ou não precisa cadastrar o projeto sozinho.
- Prefere solicitar a criação de uma nova apresentação ao responsável pela plataforma.


1.5 Usuário principal: corretor

O corretor acessa uma URL própria, sem login e senha na primeira versão.

Exemplo:

    https://app.suamarca.com.br/corretor/joao

Ele visualiza os empreendimentos publicados para ele, abre cada projeto, explora a experiência e copia o link público.

O corretor não edita o conteúdo no sistema. Alterações, correções e novos empreendimentos serão solicitados diretamente ao responsável pela plataforma.


1.6 Usuário secundário: cliente

O cliente recebe uma URL pública enviada pelo corretor.

Exemplo:

    https://app.suamarca.com.br/p/aurora?corretor=joao

O cliente não precisa criar conta, não precisa informar senha e não precisa instalar aplicativo.

Ele poderá:

- Abrir a apresentação.
- Explorar o modelo 3D ou imagem principal.
- Abrir galeria.
- Consultar localização.
- Abrir plantas.
- Explorar amenities.
- Abrir tour quando disponível.
- Falar com o corretor.
- Enviar formulário de interesse.


1.7 Responsável pela implantação dos projetos

O responsável pela plataforma será quem criará e publicará os empreendimentos.

O corretor não terá botão “Adicionar empreendimento”.

Para adicionar um novo empreendimento:

1. O corretor entra em contato.
2. Os materiais são recebidos.
3. O projeto é modelado e configurado.
4. A página é criada.
5. O empreendimento é associado ao corretor.
6. O projeto é publicado na tela inicial.


1.8 Objetivos funcionais

A primeira versão deverá permitir:

- Identificar o corretor pela URL.
- Exibir os empreendimentos contratados.
- Abrir o empreendimento selecionado.
- Carregar conteúdo específico do projeto.
- Exibir o modelo 3D quando disponível.
- Exibir fallback visual quando não houver 3D.
- Exibir galerias.
- Exibir localização.
- Exibir plantas.
- Exibir amenities.
- Exibir tour ou panorama quando disponível.
- Gerar/copiar link público.
- Enviar link por WhatsApp.
- Associar o cliente ao corretor do link.
- Receber formulário de interesse.
- Registrar o lead no banco de dados.
- Funcionar em computador, tablet e celular.


1.9 O que o cliente escolhe dentro da aplicação

O cliente poderá escolher, dentro da experiência pública:

- Visão geral.
- Modelo 3D.
- Vista frontal, lateral, posterior ou aérea, se configuradas.
- Galeria.
- Categoria da galeria.
- Localização.
- Categoria de ponto de interesse, se configurada.
- Planta ou tipologia.
- Amenity.
- Ambiente do tour.

O cliente não escolherá:

- Entre os empreendimentos do corretor.
- Fluxo de pagamento.
- Condição comercial interna.
- Unidade disponível para reserva.
- Desconto.
- Comissão.
- Dados privados.


1.10 O que o cliente faz dentro da aplicação

O caminho principal do cliente será:

1. Receber o link.
2. Clicar no link.
3. Abrir a experiência do empreendimento.
4. Visualizar a capa ou modelo principal.
5. Explorar o 3D por toque, arraste ou botões.
6. Abrir localização.
7. Abrir galeria.
8. Abrir plantas.
9. Explorar amenities.
10. Abrir tour, se houver.
11. Clicar em “Falar com o corretor” ou “Quero saber mais”.
12. Abrir WhatsApp ou preencher formulário.


1.11 O que fica fora do aplicativo na primeira versão

Não estarão presentes:

- Login do corretor.
- Senha do corretor.
- Cadastro de novos empreendimentos pelo corretor.
- Upload de arquivos pelo corretor.
- Painel administrativo do corretor.
- Fluxo de pagamento.
- Preços internos.
- Espelho de vendas.
- Status de unidades.
- Reserva de unidade.
- Compra online.
- Assinatura digital.
- CRM.
- ERP.
- Integração de estoque.
- Chat interno.
- Área privada do cliente.
- Sistema de comissão.
- Pagamento dentro do site.
- Checkout.
- Tela de gestão de leads para o corretor.
- Editor visual para o corretor.


1.12 Decisão sobre login

Não haverá login e senha na primeira versão.

O acesso do corretor será feito por uma URL personalizada, por exemplo:

    /corretor/joao

A URL será suficiente para abrir a tela com os empreendimentos contratados.

Como não haverá autenticação, a aplicação não deverá armazenar nem exibir informações confidenciais nessa área.


1.13 Decisão sobre pagamento

Não haverá pagamento dentro da aplicação.

O cliente não comprará imóvel, não pagará sinal e não fará checkout pelo site.

O botão de contato servirá para iniciar conversa com o corretor.


1.14 Resultado esperado

O corretor deverá conseguir enviar uma apresentação com aparência profissional usando um único link.

O cliente deverá conseguir explorar o projeto no navegador e encontrar uma forma clara de falar com o corretor.

2. TRD — TECHNICAL REQUIREMENTS DOCUMENT
====================================================================

2.1 Arquitetura geral

A primeira versão terá:

- Um frontend web.
- Um backend/API.
- Um banco de dados relacional.
- Um armazenamento de arquivos.
- Um domínio principal.
- Uma hospedagem centralizada.
- Um provedor de mapas.
- WhatsApp por link externo.
- Serviço de e-mail para encaminhamento de leads, se configurado.

Diagrama:

    Navegador do corretor
            |
            v
    URL /corretor/{slug}
            |
            v
    Frontend web
            |
            v
    API / Backend
       |       |       |
       v       v       v
    Banco   Storage   Mapa
       |
       v
    Leads / eventos

    Link público do cliente
            |
            v
    URL /p/{empreendimento}?corretor={corretor}
            |
            v
    Mesma aplicação, conteúdo público


2.2 Stack recomendada

Frontend:

- TypeScript.
- React.
- Next.js.
- CSS Modules ou Tailwind CSS.
- React Three Fiber.
- Three.js.

Backend:

- Node.js.
- TypeScript.
- Route Handlers do Next.js.
- API REST interna.

Banco:

- PostgreSQL.

Storage:

- Cloudflare R2, Amazon S3 ou Supabase Storage.

Hospedagem:

- Vercel para a aplicação Next.js.
- Supabase, Neon ou PostgreSQL gerenciado para o banco.
- Cloudflare R2 ou S3 para modelos 3D, imagens, plantas e vídeos.

Mapas:

- Mapbox ou Google Maps.
- A escolha deverá considerar custo, limite de uso e aparência desejada.


2.3 Domínio e hospedagem

Domínio principal de exemplo:

    app.suamarca.com.br

A aplicação inteira ficará nesse domínio.

As páginas serão rotas, não hospedagens independentes:

    /corretor/joao
    /corretor/joao/empreendimento/aurora
    /p/aurora?corretor=joao

Não será criada uma hospedagem separada para cada projeto.

O modelo 3D e os arquivos grandes deverão ficar em storage/CDN, não dentro do pacote principal da aplicação.


2.4 Login e autenticação

Decisão da primeira versão:

- Não haverá login.
- Não haverá senha.
- Não haverá sessão de usuário.
- Não haverá recuperação de senha.
- Não haverá painel protegido.

A identificação do corretor será feita pelo slug presente na URL.

Exemplo:

    /corretor/joao

O sistema consulta o corretor cujo slug é “joao” e carrega seus projetos.

A ausência de login implica as seguintes regras:

- Não armazenar dados comerciais privados.
- Não mostrar comissão.
- Não mostrar fluxo financeiro.
- Não permitir ações administrativas pela interface pública.
- Não permitir edição pelo corretor.


2.5 Pagamento

Não haverá pagamento no site.

Não haverá:

- Stripe.
- Mercado Pago.
- Checkout.
- Carrinho.
- Assinatura.
- Compra de produto.
- Reserva de imóvel.

A contratação do serviço de criação de novos empreendimentos ocorrerá fora da aplicação, por contato direto entre o corretor e o responsável pela plataforma.


2.6 Integrações da primeira versão

Integração 1 — WhatsApp:

Será usado um link no formato wa.me para abrir conversa com o corretor.

Exemplo:

    https://wa.me/5511999999999?text=...

Integração 2 — Mapas:

Será usado um provedor de mapas para mostrar localização e, se configurado, pontos de interesse.

Integração 3 — E-mail:

O formulário de interesse poderá enviar uma notificação por e-mail ao responsável configurado.

Integração 4 — Storage/CDN:

Os arquivos do empreendimento serão carregados de um storage externo otimizado.

Não haverá integração com CRM ou ERP na primeira versão.


2.7 Contrato mínimo das rotas

Rota da tela do corretor:

    GET /corretor/{corretorSlug}

Resposta esperada:

- Dados públicos do corretor.
- Lista de empreendimentos publicados.

Rota do empreendimento para o corretor:

    GET /corretor/{corretorSlug}/empreendimento/{empreendimentoSlug}

Resposta esperada:

- Dados públicos do corretor.
- Dados do empreendimento.
- Módulos disponíveis.
- URLs dos assets.
- Configuração visual.

Rota pública:

    GET /p/{empreendimentoSlug}?corretor={corretorSlug}

Resposta esperada:

- Dados públicos do empreendimento.
- Dados públicos do corretor.
- Link de contato.
- Módulos públicos.

Envio do lead:

    POST /api/leads

Campos mínimos:

- corretor_id.
- empreendimento_id.
- nome.
- telefone.
- email opcional.
- mensagem opcional.
- consentimento.
- origem.

Registro de evento:

    POST /api/eventos

Campos mínimos:

- empreendimento_id.
- corretor_id opcional.
- tipo_evento.
- secao.
- sessao_id.
- dispositivo.


2.8 Estados das rotas

Projeto publicado:

- Renderiza normalmente.

Projeto não encontrado:

- Exibe página 404 amigável.

Projeto pausado:

- Exibe mensagem de indisponibilidade.

Corretor não encontrado:

- Exibe página de acesso inválido.

Lead enviado:

- Retorna confirmação visual.

Erro no envio do lead:

- Retorna mensagem de erro e mantém os dados preenchidos no formulário.

Modelo 3D indisponível:

- Exibe imagem de fallback.


2.9 Requisitos de performance

- O carregamento inicial não deverá baixar todos os modelos 3D.
- A tela inicial carregará somente capas e dados básicos dos projetos.
- O modelo 3D será carregado quando o usuário abrir o empreendimento.
- Imagens deverão possuir miniaturas.
- Modelos deverão ser comprimidos.
- O sistema deverá mostrar estado de carregamento.
- O sistema deverá mostrar fallback quando o 3D falhar.
- A primeira tela deverá aparecer antes do carregamento de assets pesados.


2.10 Requisitos de responsividade

Desktop:

- Cards lado a lado.
- Menu horizontal.
- Visualizador 3D amplo.

Tablet:

- Cards em duas colunas ou carrossel.
- Controles de toque.

Celular:

- Cards empilhados ou carrossel.
- Menu interno recolhível.
- Botões grandes.
- WhatsApp destacado.
- Controles de 3D adaptados para toque.

3. FLUXO COMPLETO DO APLICATIVO
====================================================================

3.1 Mapa de telas

Tela A — Início do corretor

Rota:

    /corretor/{corretorSlug}

Entradas:

- URL recebida pelo corretor.

Saídas:

- Clique em empreendimento.
- Clique em WhatsApp.
- Clique em copiar link.

Tela B — Empreendimento no contexto do corretor

Rota:

    /corretor/{corretorSlug}/empreendimento/{empreendimentoSlug}

Entradas:

- Clique no card.
- Clique na aba do empreendimento.

Saídas:

- Abrir módulos.
- Compartilhar.
- Voltar.

Tela C — Empreendimento no contexto do cliente

Rota:

    /p/{empreendimentoSlug}?corretor={corretorSlug}

Entradas:

- Link recebido por WhatsApp, e-mail ou outro canal.

Saídas:

- Abrir módulos públicos.
- Falar com corretor.
- Enviar formulário.

Tela D — Modal de galeria

Abertura:

- Clique no menu Galeria.
- Clique em uma miniatura.

Saída:

- Fechar modal.
- Próxima/anterior.

Tela E — Mapa

Abertura:

- Clique em Localização.

Saída:

- Abrir mapa externo.
- Retornar ao empreendimento.

Tela F — Plantas

Abertura:

- Clique em Plantas.

Saída:

- Filtrar tipologia.
- Ampliar planta.
- Baixar se autorizado.
- Fechar visualizador.

Tela G — Amenities

Abertura:

- Clique em Amenities.

Saída:

- Escolher amenity.
- Ver conteúdo.
- Voltar à lista.

Tela H — Tour

Abertura:

- Clique em Tour.

Saída:

- Escolher ambiente.
- Avançar.
- Voltar.
- Fechar tour.

Modal I — Compartilhamento

Abertura:

- Clique em “Compartilhar com cliente”.

Saída:

- Copiar link.
- Abrir WhatsApp.
- Fechar modal.

Modal J — Formulário de lead

Abertura:

- Clique em “Falar com corretor”.
- Clique em “Quero saber mais”.

Saída:

- Enviar formulário.
- Fechar formulário.


3.2 Fluxo do corretor — entrada

1. O corretor abre sua URL principal.
2. A aplicação identifica o slug do corretor.
3. O backend busca o corretor ativo.
4. O backend busca os empreendimentos publicados desse corretor.
5. A tela inicial é renderizada.
6. Os cards são exibidos.

Se o slug não existir:

- O sistema exibe “Corretor não encontrado”.

Se não houver projetos publicados:

- O sistema exibe “Nenhum empreendimento disponível”.
- O contato do responsável pela plataforma poderá ser exibido.


3.3 Fluxo do corretor — abrir projeto pelo card

1. O corretor vê o card do projeto.
2. Clica em “Ver empreendimento”.
3. O navegador muda para a rota do projeto.
4. O backend busca os dados pelo slug.
5. O frontend carrega o cabeçalho.
6. O frontend carrega os módulos disponíveis.
7. O visualizador 3D começa a carregar, se existir.
8. O corretor pode interagir com a página.


3.4 Fluxo do corretor — abrir projeto pela aba superior

1. O corretor vê as abas no menu superior.
2. Clica no nome do projeto.
3. O navegador navega para a rota desse projeto.
4. A tela anterior permanece no histórico do navegador.
5. A seta nativa de voltar pode retornar à tela anterior.


3.5 Fluxo do corretor — copiar link geral

1. O corretor está na tela do projeto.
2. Clica em “Compartilhar com cliente”.
3. Abre o modal de compartilhamento.
4. O sistema monta a URL pública.
5. A URL recebe o slug do empreendimento e o slug do corretor.
6. O corretor clica em “Copiar link”.
7. O navegador copia a URL.
8. O botão muda temporariamente para “Link copiado”.
9. O corretor fecha o modal ou abre o WhatsApp.


3.6 Fluxo do corretor — enviar pelo WhatsApp

1. O corretor abre o modal.
2. Clica em “Enviar pelo WhatsApp”.
3. O sistema cria a mensagem.
4. O sistema abre o WhatsApp Web ou aplicativo.
5. O corretor escolhe o contato.
6. O corretor confirma o envio dentro do WhatsApp.

O site não enviará a mensagem sem a ação final do corretor no WhatsApp.


3.7 Fluxo do cliente — abrir link

1. O cliente recebe o link.
2. Clica no link.
3. O navegador abre a rota pública.
4. A aplicação identifica o empreendimento.
5. A aplicação identifica o corretor pelo parâmetro.
6. O backend retorna somente conteúdo público.
7. O cabeçalho público é exibido.
8. A visão geral do empreendimento é exibida.
9. O menu geral de projetos não é exibido.
10. O botão “Voltar para empreendimentos” não é exibido.


3.8 Fluxo do cliente — explorar 3D

1. O cliente vê o visualizador.
2. O modelo começa a carregar.
3. Enquanto carrega, aparece o indicador.
4. Quando termina, o modelo fica interativo.
5. O cliente arrasta para girar.
6. O cliente usa pinça ou rolagem para zoom.
7. O cliente pode clicar em vista frontal, lateral, posterior ou aérea.
8. O cliente pode clicar em tela cheia.
9. O sistema registra eventos de interação.


3.9 Fluxo do cliente — galeria

1. O cliente clica em Galeria.
2. A galeria é aberta.
3. O cliente vê miniaturas.
4. Clica em uma imagem.
5. A imagem abre em destaque.
6. O cliente pode avançar ou voltar.
7. O cliente fecha a galeria.
8. O sistema retorna ao estado anterior.


3.10 Fluxo do cliente — plantas

1. O cliente clica em Plantas.
2. O sistema lista as plantas públicas.
3. O cliente escolhe uma tipologia.
4. A lista é filtrada.
5. O cliente abre a planta.
6. O visualizador permite zoom.
7. O cliente fecha a planta.
8. O sistema retorna à lista.


3.11 Fluxo do cliente — localização

1. O cliente clica em Localização.
2. O mapa é carregado.
3. O marcador do empreendimento aparece.
4. O endereço é exibido.
5. Os pontos cadastrados aparecem.
6. O cliente pode clicar em um ponto.
7. O cliente pode clicar em “Abrir no mapa externo”.
8. O navegador abre o provedor de mapas.


3.12 Fluxo do cliente — amenities

1. O cliente clica em Amenities.
2. O sistema mostra a lista.
3. O cliente clica em uma amenity.
4. A imagem ou panorama é aberto.
5. A descrição é exibida.
6. O cliente pode clicar em “Ver no modelo”, quando houver coordenada.
7. O cliente pode voltar à lista.


3.13 Fluxo do cliente — contato via WhatsApp

1. O cliente clica em “Falar com corretor”.
2. O sistema identifica o WhatsApp vinculado ao corretor.
3. O sistema monta uma mensagem com o empreendimento.
4. O WhatsApp abre.
5. O cliente envia a mensagem pelo WhatsApp.


3.14 Fluxo do cliente — formulário

1. O cliente clica em “Quero saber mais”.
2. O modal abre.
3. O cliente informa nome.
4. O cliente informa telefone.
5. O cliente informa e-mail, se quiser.
6. O cliente escreve uma mensagem, se quiser.
7. O cliente marca consentimento.
8. O cliente clica em “Enviar”.
9. O frontend valida os campos.
10. A API recebe os dados.
11. O backend salva o lead.
12. O backend dispara e-mail, se configurado.
13. O sistema exibe confirmação.


3.15 Fluxo de erro do formulário

Se nome estiver vazio:

- Exibir “Informe seu nome”.
- Não enviar a requisição.

Se telefone estiver vazio:

- Exibir “Informe seu telefone ou WhatsApp”.
- Não enviar a requisição.

Se o backend falhar:

- Exibir mensagem de erro.
- Manter os dados no formulário.
- Permitir tentar novamente.

4. BRIEFING DE DESIGN E INTERFACE
====================================================================

4.1 Direção visual

A interface deverá transmitir:

- Arquitetura.
- Sofisticação.
- Clareza.
- Exclusividade.
- Tecnologia.
- Segurança.
- Conforto.

A interface não deverá competir com o modelo 3D e as imagens. Os controles precisam ser discretos, mas facilmente reconhecíveis.


4.2 Paleta base recomendada

A paleta abaixo é a base da plataforma. Cada empreendimento poderá possuir imagens próprias, mas a estrutura de interface deverá manter consistência.

Cor de fundo principal:

    #0F1115

Uso:

- Fundo da tela inicial.
- Fundo de áreas de navegação.
- Fundo de modais escuros.

Cor de superfície:

    #181C23

Uso:

- Cards.
- Painéis.
- Menu lateral.
- Modal.

Cor de superfície elevada:

    #232936

Uso:

- Card em hover.
- Item selecionado.
- Painel ativo.

Cor de texto principal:

    #F5F7FA

Uso:

- Títulos.
- Nomes dos empreendimentos.
- Botões principais.

Cor de texto secundário:

    #AEB6C2

Uso:

- Descrições.
- Legendas.
- Informações complementares.

Cor de texto discreto:

    #7C8796

Uso:

- Metadados.
- Instruções secundárias.

Cor de destaque principal:

    #C9A66B

Uso:

- Botão principal.
- Linha ativa.
- Destaque de empreendimento.
- Hover de elementos importantes.

Cor de destaque clara:

    #E2C28E

Uso:

- Hover do botão principal.
- Ícones ativos.
- Títulos de seção selecionados.

Cor de sucesso:

    #3DBB82

5. ESQUEMA DE BACK-END E BANCO DE DADOS

5.1 Princípio de funcionamento

O corretor não editará diretamente o banco de dados pela interface.

O responsável pela plataforma fará o cadastro e a publicação dos dados dos projetos usando procedimento interno.

A aplicação pública somente consultará os dados publicados.

O formulário de lead fará uma inserção controlada na tabela de leads.

Eventos de navegação poderão ser registrados para medir acessos e interações.


5.2 Diagrama de entidades

    CORRETOR
       |
       | 1:N
       v
    EMPREENDIMENTO

       | 1:N

       +---------- PLANTA

5.3 Tabela CORRETOR

Armazenar os dados públicos do corretor usados na página inicial, no link do cliente e no contato.

Campos:

- nome_comercial: varchar, opcional.
- foto_url: text, opcional.
- creci: varchar, opcional.
- telefone: varchar, opcional.
- whatsapp: varchar, obrigatório para botão de contato.
- email: varchar, opcional.
- mensagem_apresentacao: text, opcional.
- logo_url: text, opcional.
- ativo: boolean, obrigatório, padrão true.
- criado_em: timestamp.
- atualizado_em: timestamp.

- O slug será usado na URL.
- O corretor deve possuir WhatsApp para habilitar o botão.

7. DEFINIÇÃO FINAL DA PRIMEIRA VERSÃO
====================================================================

A primeira versão será composta por:

- Uma aplicação web.
- Uma URL de acesso do corretor.
- Uma tela inicial com os empreendimentos contratados.
- Três empreendimentos inicialmente publicados.
- Uma página interativa reutilizável para cada empreendimento.
- Um link público por empreendimento.
- Identificação do corretor no link.
- Visualização 3D ou fallback.
- Galeria.
- Localização.
- Plantas.
- Amenities.
- Tour quando houver conteúdo.
- Compartilhamento por copiar link.
- Compartilhamento via WhatsApp.
- Botão de contato.
- Formulário de lead.
- Registro de leads.
- Registro básico de eventos.
- Banco de dados.
- Storage para arquivos.
- Hospedagem centralizada.
- Layout responsivo.

Não haverá login, pagamento, fluxo financeiro, disponibilidade de unidades, CRM, ERP, cadastro autônomo de projetos ou painel de edição para o corretor.

O corretor utilizará o produto como uma ferramenta pronta de apresentação. Cada novo empreendimento será criado, modelado, configurado e publicado pelo responsável pela plataforma mediante solicitação e contratação.
